1 Executive Summary & Problem Resolution

Higher education institutions face systemic operational friction caused by disconnected legacy systems. Academic grading, student fee ledgers, exam eligibility validation, hostel bed allocations, and dynamic attendance monitoring are frequently siloed in separate software packages or paper records. This leads to fee leakage, unauthorized exam access, inaccurate transcripts, and administrative latency.

The Resolution: UAMS was engineered as a single, unified enterprise administration platform that interconnects academic policy, real-time banking/mobile payments, campus operations, and role-based access control (RBAC). The system guarantees policy integrity at code level: students cannot take exams without verified clearance, grades follow institutional continuous assessment (CAT) formulas, and M-Pesa payments reconcile automatically without human error.

3 Step-by-Step Implementation Journey

The platform was designed and built systematically across seven modular engineering phases:

Step 1: Relational Data Schema & Institutional Model Design

Defined third-normal-form (3NF) relational tables with strict foreign keys to represent university operations:

  • students & staff: Unified identity schema storing admission numbers, programs, departments, and roles.
  • courses & enrollments: Academic course catalog with prerequisite validations and credit load tracking.
  • grades: Continuous Assessment Test (CAT) and Final Examination scores linked to academic sessions.
  • finance_accounts & transactions: Ledger tracking student invoices, M-Pesa STK receipts, and bank transfers.
  • hostels & library_loans: Room capacity allocation and book circulation with automatic fine accruals.
  • audit_logs: Immutable event ledger tracking administrative and financial mutations.

Step 2: Role-Based Access Control (RBAC) & Authentication Overhaul

Engineered role guards ensuring that users only access functionality permitted by institutional charter:

  • 6 Roles Supported: Student, Lecturer, Registrar, Finance Officer, Dean, and System Administrator.
  • Role Normalization: Built a robust normalizer (normalizeRole) in both backend and frontend to map varied case representations to canonical role enums.
  • Sandboxed Evaluator Controls: Isolated demonstration test credentials into a dedicated defense sandbox mode (disabled in production) with sensitive tokens purged from localStorage to prevent XSS exfiltration.
  • Token Security: Implemented HMAC-SHA256 signed session token verification (HS256) with timing-safe signature comparison, 24-hour expiration, and fail-closed production secret policy.

Step 3: Academic Policy Engine & Weighted GPA Calculation

Implemented the institution's formal grading and progression regulations in src/lib/academic/policy.ts:

  • CAT/Exam Weighting: Default 30% Continuous Assessment + 70% Final Exam, with dynamic institutional toggle to 40%/60% depending on faculty policy.
  • 4.0 GPA Calculation: Weighted grade point calculations based on credit units (Grade A = 4.0, B = 3.0, C = 2.0, D = 1.0, F = 0.0).
  • Standing Classifier: Automatic award classification (First Class Honours ≥ 3.70, Second Class Upper ≥ 3.00, Second Class Lower ≥ 2.50, Pass ≥ 2.00).
  • Exam Gatekeeping: Dynamic checks verifying ≥75% lecture attendance threshold and ≥80% fee payment clearance before exam admittance.

Step 4: Financial Automation, M-Pesa STK & Bank Reconciliation

Automated revenue collection and ledger balancing to eliminate manual cashier delays:

  • Safaricom Daraja STK Push Simulator: Strict phone sanitization normalizing numbers to Kenyan 254XXXXXXXXX format and validating real-time push payloads.
  • Idempotent Webhook Handler: Transaction cache verifying receipt tokens so duplicate Safaricom callback requests do not double-credit student accounts.
  • Multi-Format Bank Reconciliation: Built an automated parser capable of ingesting raw CSV/TXT bank statements (KCB, Equity, Co-op), detecting student admission numbers via regex, and auto-matching amounts against pending fee balances.

Step 5: Campus Operations & Real-Time Modules

Expanded the platform beyond traditional record keeping into active daily campus operations:

  • Dynamic QR Attendance Projector: A real-time token projector for lecture halls generating expiring QR codes that students scan on mobile devices to register physical attendance.
  • Exam Clearance & Official Cards: Real-time clearance check providing one-click downloadable vector PDF Exam Cards containing security barcodes, student portraits, and venue schedules.
  • Hostel & Bed Allocation: Room allocation engine preventing overbooking by locking bed capacity in male and female halls.
  • Library Circulation: Book checkouts and check-ins with automatic KES 20/day overdue fine computation.
  • Multi-Channel Broadcast Dispatcher: Dispatch portal for campus-wide emergency SMS and academic email announcements.

Step 6: Docker Orchestration & Multi-Tier Topology

Configured standardized container orchestration in docker-compose.yml:

  • Frontend Container: Optimized Next.js build served on port 3000.
  • Backend API Container: Node/Express microservice served on port 4000.
  • Database: PostgreSQL 15 container initialized with automated DDL migration scripts and seed data.
  • Offline Resilient Fallback: If database containers are offline during local offline presentations, the API automatically shifts to an in-memory synchronized data layer ensuring zero downtime during supervisor reviews.

Step 7: Automated Test Suite & Security Assurance Verification

Engineered 36 automated test specifications across frontend and backend verifying business logic, authorization invariants, and enterprise security controls:

  • Backend Test Suite (9/9 Passed): Role normalization, credential validation, token encryption/decryption, route protection middleware, health endpoints, tampered HMAC signature rejection, and token expiration.
  • Frontend Test Suite (27/27 Passed): Exam fee clearance rules, library fine calculations, hostel capacity guards, 4.0 weighted GPA formulas, honors classifications, policy engine CAT/Exam splits, Safaricom M-Pesa STK payload validation & callback settlement, zero hardcoded fallback secrets, brute-force rate limiting, XSS session sanitization, IDOR/BOLA student data isolation, CSRF origin verification, permission-based RBAC capability guards, and immutable audit event ledger logging.
